# Status-specific controls and one persistent order card

User approved showing only actions valid for the current order state and updating the existing card rather than posting status-message duplicates. Keep view order/customer details available. Awaiting-payment orders can cancel; payment-review orders can approve, flag an issue, or cancel; paid orders can accept, flag an issue, or record a refund; accepted orders can start, flag an issue, or record a refund; processing orders can complete, flag an issue, or record a refund; completed orders can return to processing or record a refund. Issue orders can resume/refund only after payment verification; otherwise cancel. Cancelled/refunded orders have read-only controls. Domain transaction validation remains authoritative, including for stale buttons.

Persist the canonical card by bot identity and full order UUID, with admin chat, player topic, message ID, media kind and current receipt ID. Refresh text cards with editMessageText, receipt cards with editMessageCaption, and replace/add receipt media in the same message with editMessageMedia. Use the latest database state and latest receipt, even when an old status notification or old receipt job is being delivered. A single Telegram worker serializes view/status renders per order; persistent mappings survive restarts. A moved/replaced player topic must never edit the old-topic card. Only a definite deleted-message error permits sending a replacement. Unchanged edits count as success; network/other API failures retry without posting a replacement.

New card identity is saved before marking its durable notification delivered, so a delivery-record failure retries by editing that card. Existing legacy delivery rows are preserved; they are not used as canonical card identities because older bot migrations can reuse message numbers. Adopt only the three explicitly verified current-bot mock photo cards. Preserve customer-visible chat and all existing order/payment states.
